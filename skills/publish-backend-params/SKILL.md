# 发布后台参数

在当前 crslice 工作区发布后台参数，本机仓库通常为 `C:/work/crslice`。发布目标为 `origin` 的当前同名分支，标签格式为 `release-v3.0.0-fixN`。用户调用本技能要求发布即授权拉取、rebase、创建标签及推送，无需重复确认；用户仅要求编写技能时只创建技能。

## 发布流程

1. 读取仓库指令，检查 `git status --short`、当前分支、`origin` 地址和是否已有 merge/rebase 正在进行。不能在 detached HEAD 上发布。不改变当前分支，也不把当前提交推送到其他分支。
2. 发布既有提交需要干净的工作区。若有本次任务已授权且应纳入发布的修改，检查并验证后只提交这些修改；其他未提交改动需要先明确处理方式，不自动全量暂存、丢弃或 stash。这条规则不限制用户在当前会话已明确授权的处理方式。
3. 执行 `git -c rebase.autoStash=false pull --rebase origin <当前分支>`，不依赖可能指向其他分支的 upstream。每条 Git 命令都检查退出码，失败不继续打标签。若有 rebase 冲突，保留双方意图解决并验证后继续；无法判断的冲突保留现场并说明具体阻塞，不跳过提交或强制覆盖。远端同名分支不存在时，说明情况并确认首次发布目标。
4. 完成拉取及必要验证后，运行 `git fetch --tags origin`，并用 `git ls-remote --tags origin 'refs/tags/release-v3.0.0-fix*'` 读取远端标签。检查本地及远端该系列标签，以两者最大数字加一命名。只接受完整匹配 `^release-v3\.0\.0-fix([0-9]+)$` 的名称，忽略 annotated tag 的 `^{}` 行、其他版本及非数字后缀。采用整数比较，不能按字符串排序；例如 fix9 和 fix17 得到 fix18，fix99 得到 fix100。`fix17` 是示例，不是固定标签。系列没有任何标签时从 fix1 开始。
5. 记录待发布的 `git rev-parse HEAD`，确认工作区干净、分支未切换，并检查候选标签在本地及远端均不存在。默认用 `git tag <新标签> <已记录的提交>` 创建 lightweight tag，沿用仓库既有惯例；不移动或覆盖已有标签。
6. 使用一次原子推送发布两个明确的 ref：`git push --atomic origin HEAD:refs/heads/<当前分支> refs/tags/<新标签>:refs/tags/<新标签>`。这样分支和标签一起成功或一起失败。不要使用 `--force`、`--force-with-lease`、`--tags` 或 `--mirror`。服务器不支持原子推送时报告原因，说明顺序推送可能只成功一部分，在用户接受该方式后再执行。
7. 用 `git ls-remote origin refs/heads/<当前分支> refs/tags/<新标签>` 核对远端两个 ref 都指向记录的提交，再检查 `git status --short`。只有远端分支与标签均核验通过才报告发布成功。

## 失败与重试

- 网络超时或推送失败后先读取远端实际状态，不因返回错误就假定没有发布成功，也不立即再生成一个标签。
- 推送因远端分支前进或标签被占用而拒绝时，先确认远端状态。对于本次创建且尚未成功发布的本地标签，可删除该本地标签后重新拉取、验证、计算编号、打标签及推送；不删除远端标签或用户原有标签。
- 每次调用最多自动重试一次发布竞争；再次失败则保留提交并报告具体状态，避免不断生成发布标签。
- 原子推送已成功且核验通过后，本次发布结束；核验暂时无法完成则报告待核验，不重发。

## 完成反馈

简要报告分支、发布提交哈希、新标签、推送与远端核验结果。若失败，说明已完成的步骤、本地标签是否存在、远端实际状态以及需要处理的问题。
